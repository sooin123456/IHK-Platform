# 협업 검토 잠금 상태의 반복 변경 수정 — 검증 기록

## 반영 결과

동일한 검토 잠금 상태를 반복 조회할 때 Yjs 내부 식별자가 불필요하게 늘어나는 문제를 수정했다. `freeze.ts`의 작은 공통 함수가 실제로 달라진 필드만 변경하도록 하고, 기존 일곱 경로에서 재사용한다. 외부 잠금, 같은 서버의 검토 준비, 승인된 도면의 상태 확인 모두 기존 권한·잠금·검증 판단을 유지한다.

수정 범위는 `platform/collaboration/src/freeze.ts`, `platform/collaboration/src/server.ts`, `platform/tests/drawing-review-freeze.test.mjs` 세 파일이다. 새 의존성·DB 변경·배포는 없다. 기존 dirty 파일의 정확한 수정 전 사본과 비교했고, 이전 DWG 검증 대상17파일 해시는 모두 유지했다.

## 검증

| 확인 | 결과 |
| --- | --- |
| 수정 전 기존 검토·잠금 검사 | 27/27 통과 |
| 새 검사 RED | 29개 중5개 예상 실패: 실제4경로의 바이트 증가와 미구현 함수 |
| 수정 후 검토·잠금 검사 | 29/29 통과 |
| 협업 서버·클라이언트·잠금·네이티브 회귀 | 140/140 통과 |
| 기존 도면·이슈·앵커 검사 | Vite 별칭 로더에서17/17 통과 |
| 협업 TypeScript 검사 | 종료0, 진단 없음 |
| 독립 작업 검토 및 최종 통합 검토 | 모두 승인, Critical/Important/Minor 없음 |

29개 focused 검사는140개 회귀에 포함된다. 최종 서로 다른 검사는157개이며 실패·건너뜀·취소가 없다. 전체 애플리케이션/실제 브라우저 출시 검증을 의미하지 않는다.

추가 검사 과정의 실행기 문제도 기록했다. 기존 도면 테스트를 plain Node로 실행하면 `~` 별칭을 찾지 못했고, 첫 Vite 시도는 비동기 테스트 전에 실행기를 닫았다. 기존 Vite 별칭 처리와 Node 테스트 `after` 종료를 사용한 최종 실행에서17개 모두 통과했다. 애플리케이션 코드나 실패 검사를 우회하지 않았다. 구현자 raw 로그에는 터미널 캡처 종료 표시가 남을 수 있으며, 최종 controller 로그는 파이프 캡처로 테스트 진단 없이 통과했다.

실행 중인 미리보기는 기존 PID80284/4173과 HTTP200을 유지했다. 이번 수정은 로컬 소스에만 있으며 미리보기를 재빌드하거나 운영 배포하지 않았다.

최초 협업 상태의 원자적 저장, 임시 잠금의 미저장 식별자 노출, 실제 상태 전환의 저장 순서 문제는 **아직 해결 완료가 아니다**. [후속 계약 진단](2026-09-06-collaboration-provenance-followup.md)에 세 로더, Viewer/승인 열람, 검토 준비 lease, 첫 동기화 반례와 필수 검증을 기록했다. 실제 로그아웃·오프라인 두 사용자 복원도 R2에 남아 있다. DWG 재저장 작업·다운로드·납품 검증(R4), 승인본 기반 템플릿/납품 패키지(R5)는 전체 목표에서 계속 진행한다.

## 이번 단위의 결정과 비용

1. 반복 승인 없이 승인된 범위의 로컬 구현을 진행하되 stage/commit/merge/push/deploy 권한은 추정하지 않았다. 비용: 운영에는 자동 반영되지 않는다.
2. 불필요한 반복 쓰기를 독립 수정으로 수용하되 전체 재접속 해결로 표시하지 않는다. 잘못 판단하거나 과장하면 정상 재접속 거절이 남는다. 따라서 R2 완료 게이트는 열어 둔다.
3. HEAD 전체 diff가 아니라 정확한 dirty 사본으로 검토한다. 잘못 비교하면 기존 사용자 변경을 덮거나 이번 수정으로 오인할 수 있어 사본·해시로 확인했다.
4. 커밋되지 않은 증거와 linked worktree를 보존한다. 통합 선택 메뉴·정리는 반복 승인을 그만하라는 사용자 지침에 따라 실행하지 않았다. 비용: 로컬 통합·배포 단계는 남는다.
5. 원래 glob 밖의 클라이언트 브리지 검사와 기존 도면 검사도 추가 검증했다. 새 기능 범위는 늘리지 않았다.
6. 기존 도면 검사의 별칭 문제는 설치된 Vite로 검증하고 관련 없는 import를 변경하지 않았다. 잘못된 실행기는 결함을 숨길 수 있으므로 실패 시도와 최종 실제17개 검사를 구분해 남겼다.
