# 승인 네이티브 도면의 시험용 DWG 내보내기

2026-09-06 · 개발/검증 기록 · 운영 배포 아님

## 범위

승인된 네이티브 단일 캔버스에서 실제 DWG를 비동기로 생성하고, 승인·원본 근거와 검증 보고서를 함께 내려받는 수직 기능이다. 기존 고객 DWG를 가져와 편집하고 재저장·납품하는 전체 기능의 완료를 의미하지 않는다. 출력 자격은 계속 `experimental-unqualified`이다.

## 구현

- PostgreSQL의 멱등 요청, 최대 3회 시도, 만료 토큰, 변경 불가한 산출물·완료 기록. 현재 권한과 승인 원본을 서버에서 다시 검사한다.
- 기존 ACadSharp 3.7.1/.NET 8 변환기를 실행하는 Node 작업자. 새 큐 제품·버킷·패키지 의존성 없이 기존 기반을 재사용했다.
- 4개 파일을 DB에 먼저 등록한 후 비공개 Storage에 저장하고 크기·SHA-256을 재검증한다. 불확실한 업로드는 열린 상태로 보존하며 완료 처리하거나 삭제하지 않는다.
- 기존 내보내기 창의 `DWG (시험)`, 상태 복원, 같은 요청 재확인, `DWG / 도면 데이터 / 승인·원본 근거 / 검증 보고서` 다운로드.
- 다운로드는 사용자 권한 검사 → 제한된 스트림 수신·해시 검증 → 권한 재검사 순서다. 브라우저에 Storage URL이나 서비스 자격 증명을 전달하지 않는다.

## 실제 실행에서 수정한 오류

1. 잠금을 기다리는 동안 만료된 작업을 이전 시각으로 실패 처리하던 경계와 NULL 입력 검증.
2. 변환 프로세스 종료 전에 임시 파일을 정리할 수 있던 문제, macOS 임시 경로의 `/var` → `/private/var` 별칭.
3. 응답 헤더 뒤에서 멈춘 업로드·다운로드의 시간·크기 제한과 실제 취소, 불확실한 업로드의 잘못된 완료 판단.
4. 상태 조회 실패 후 같은 작업 ID로 재시도하면 계속 로딩으로 남는 UI, 중복 클릭이 진행 중 요청을 취소하는 순서.
5. React Router 리소스 경로의 일반 export 때문에 서버 전용 코드가 클라이언트 빌드에 남는 문제. 서버 처리기를 `.server.ts`로 분리했다.
6. 실제 Storage의 `400 InvalidMimeType`: DWG는 이미 허용된 `application/octet-stream`으로 저장한다. 검증된 다운로드의 MIME은 `application/acad`이며 버킷 권한을 넓히지 않았다.

기존 광범위 경로 테스트의 4개 오래된 기대값도 수정했다. 네이티브 카탈로그 추가, 더 좁은 측정 패널 활성 조건, 공유 치수 표시 함수의 실제 동작을 검사하며 제품 동작을 바꾸거나 기존 검증을 제거하지 않았다.

## 검증 상태

최종 검사 통과. 단일 종단 시나리오뿐 아니라 기존 M1 전체 브라우저 흐름에서도 실제 로그인·네이티브 예제·심볼 추가·검토·승인·A3 PDF 뒤에 DWG 흐름을 이어서 통과했다.

| 검사 | 결과 |
| --- | --- |
| 최종 관련 회귀 테스트 | 309 통과, 실패·건너뜀 0, 16.84초 |
| 앱 typegen/TypeScript, 앱 배포용 빌드, 협업·DWG 작업자 빌드 | 모두 exit 0 |
| 실제 M1/M2/M5 DB·Storage 게이트 | 5 통과, 실패 0; 환경 미설정 알림용 조건부 검사 2개만 건너뜀 |
| 단일 네이티브 예제 → DWG 종단 시나리오 | 1 통과, 1.1분 |
| 최종 전체 M1 Chromium 브라우저 | 23 통과, 실패·건너뜀 0, 3.4분 |

동결된 실제 파일과 수치는 같은 이름의 증거 폴더에 있다: `verification.json`, `native.dwg`, `source-manifest.json`, `authority.json`, `native-report.json`, `completed.png`, `native-measured-plan-a3.pdf`, `hash-index.json`. 해시 목록은 새로 생성한 파일 바이트로 계산했고, 4개 다운로드의 해시는 서버 완료 기록과 대조했다. 인증 토큰·서비스 자격 증명·브라우저 추적 파일은 이 공개 증거 묶음에 넣지 않았다.

확인한 동작:

- 실제 POST 승인, 상태 조회 오류 1회 주입, 같은 요청 ID 재확인 후 조회 재개, 창 닫기·다시 열기.
- 별도 클라이언트의 두 실제 작업자가 같은 큐를 처리할 때 `completed + idle`; 실제 PostgREST/Storage/.NET 사용.
- 4개 다운로드의 원본 크기·해시와 완료 기록 일치, AC1024 헤더. HTTP의 JSON charset/Brotli 압축과 압축 해제 후 파일 바이트는 구분하여 검사한다.
- Viewer의 승인 파일 다운로드 성공, 직접 Storage 접근 거부, 외부 사용자 및 권한 철회 뒤 다운로드 거부.
- 두 번째 작업에서 실제 30초 만료를 통과하도록 별도 연결이 프로젝트 잠금을 유지한다. 만료 전에 해당 실패 RPC가 잠금 대기 중임을 확인하고, 해제 뒤 `stale`과 상태 불변을 확인한다.
- 다음 작업자가 재처리해도 이전 열린 업로드 시도는 보존된다. 이전 시도는 새 완료 기록을 재사용할 수 없고, 실제 게시 RPC 재호출에도 작업별 완료 기록은 1개다.
- 기존 시나리오의 PDF/IFC 원본 보존과 Viewer 편집 거부 검사가 그대로 유지된다.

의도적으로 주입한 상태 조회 오류와 권한 철회에 대한 서버의 거부 로그는 성공/오류 없는 연결로 위장하지 않는다. 별도 CAD 프로그램의 판독이나 수신자의 납품 승인 결과는 만들지 않았다.

## 재현과 운영 경계

`platform/native-dwg-worker/README.md`의 실제 변환기 절대 경로를 설정하고 기존 M1 disposable 명령을 실행한다. 테스트는 표시된 로컬 DB·Storage에서만 수행하며 최종 정리는 해당 일회용 스택으로 한정한다. 운영 DB, 파일, 배포에는 변경을 적용하지 않았다.

독립 검토를 통과한 뒤 해당 일회용 DB·Storage의 종료·삭제를 확인했다. 재생성 가능한 테스트 데이터만 정리했으며 검증 파일과 프로젝트 원본은 보존했다.

웹앱 배포만으로 변환 작업이 실행되지는 않는다. 운영 릴리스에는 마이그레이션과 고정된 변환기가 설치된 장기 실행 작업자 호스트가 함께 필요하다.

## 남은 목표

1. 외부에서 작성된 고객 DWG의 명시적 객체 선택 → 편집 → 재저장. 원본 보존과 미지원 객체·블록·레이아웃·폰트·외부 참조의 보존 범위를 검사해야 한다.
2. 독립 CAD에서 열기·재생성·재저장·출력 및 실제 수신자 승인으로 납품 적격성을 확인해야 한다.
3. 실무 템플릿, 개정 비교, 물량·금액 근거 및 납품 패키지를 최종 사용자 흐름으로 완성해야 한다.

비용·라이선스 계약이나 운영 배포가 필요한 결정은 별도 경계이며, 이번 로컬 개발로 승인된 것으로 간주하지 않는다.
