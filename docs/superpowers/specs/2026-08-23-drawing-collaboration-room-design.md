# 1HK 도면 협업실 설계

기준일: 2026-08-23

## 1. 목표

1HK Platform의 프로젝트 안에서 참여자가 IFC 3D와 PDF 2D를 같은 방식으로 검토한다. 사용자는 도면의 실제 위치를 선택해 이슈를 만들고, 댓글·담당자·기한·상태를 관리하며, 개정 뒤에도 누가 어떤 근거로 무엇을 해결했는지 확인할 수 있어야 한다.

완료 장면은 다음과 같다.

1. 설계자가 IFC와 PDF를 프로젝트에 등록한다.
2. 적산 담당자가 IFC 객체 또는 PDF 영역을 선택해 하나의 검토 이슈에 근거로 연결한다.
3. 현장·구매·검토 담당자가 같은 이슈에서 댓글과 파일 근거를 확인한다.
4. 담당자가 해결을 요청하고 owner 또는 reviewer가 최종 종료한다.
5. 새 도면 개정이 등록되어도 과거 이슈와 앵커는 보존되며, 유효하지 않은 앵커는 자동 이전하지 않고 재연결 대상으로 표시한다.

## 2. 채택 접근법

### 채택: 기존 프로젝트 안의 통합 도면 협업실

- 기존 React Router 프로젝트·파일·회원·IFC 뷰어·Supabase RLS를 재사용한다.
- `/projects/:projectId/drawings`를 도면 파일함으로, `/projects/:projectId/drawings/:fileId`를 협업실로 사용한다.
- IFC와 PDF는 서로 다른 렌더러를 사용하지만 이슈·앵커·댓글·상태 모델은 공유한다.
- 실시간 갱신은 초기 규모에 맞춰 Supabase Postgres Changes를 프로젝트별 필터로 사용한다. 동시 접속 규모가 실제로 병목이 될 때만 Broadcast로 교체한다.

### 기각: 별도 마이크로프런트엔드·Go 협업 서버

현재 인증·권한·파일 저장·프로젝트 계보를 중복 구현하게 된다. 실측 병목이 없으므로 도입하지 않는다.

### 기각: 대형 BIM/CDE 오픈소스 전체 도입

기존 원본·수량·승인 계약과 충돌하고 제품 통제면이 과도하게 커진다. 필요한 뷰어 동작만 현재 코드에 추가한다.

## 3. 제품 구조

### 프로젝트 홈

- 프로젝트 카드의 기본 `열기`는 최신 도면 협업실로 이동한다.
- 카드에서 미해결 이슈 수, 내 담당 이슈 수, 마지막 도면 개정 시각을 보여준다.
- `도면`, `내역`, `검토`, `자재`, `구성원`은 서로 다른 업무 화면으로 유지한다.

### 도면 파일함

- IFC와 PDF만 도면으로 분류한다.
- 파일명, 형식, 개정, 등록자, 등록 시각, 미해결 이슈 수를 표시한다.
- 같은 종류의 새 파일은 기존 파일 개정 그래프를 그대로 사용한다.
- 원본은 불변이며 교체하지 않는다.

### 협업실

- 데스크톱: 왼쪽 도면/개정 목록, 가운데 뷰어, 오른쪽 이슈 패널.
- 모바일: 도면 보기와 이슈 패널을 탭으로 전환하며 작성 버튼은 하단에 고정한다.
- 공통 도구는 `선택`, `핀/영역 지정`, `맞춤 보기`, `이슈 목록`만 제공한다.
- 자유 곡선 드로잉, 도형 편집기, 동시 커서, 음성 채팅은 첫 완성 범위에서 제외한다.

### IFC 렌더러

- 기존 `web-ifc`와 Three.js 렌더러를 재사용한다.
- 선택한 객체의 canonical Revit Element ID 또는 확인된 IFC GlobalId를 앵커에 저장한다.
- 카메라 위치·타깃·선택 객체를 함께 저장해 이슈 클릭 시 같은 장면으로 복원한다.
- 객체 식별이 불확실하면 이슈를 만들 수 없고 `근거 확인 필요`를 표시한다.

### PDF 렌더러

- `pdfjs-dist`를 고정 버전으로 추가하고 클라이언트에서 페이지를 렌더링한다.
- 원본 PDF는 private Storage의 단기 signed URL로만 읽는다.
- 앵커 좌표는 픽셀이 아니라 페이지 기준 0~1 정규화 좌표 `(x, y, width, height)`로 저장한다.
- 확대·회전·화면 크기가 바뀌어도 같은 영역을 표시한다.
- 텍스트 인식이나 OCR은 하지 않는다.

## 4. 데이터 계약

### `lukas_drawing_issues`

- `id`, `project_id`, `title`, `description`
- `priority`: `low | normal | high | urgent`
- `status`: `open | in_progress | resolution_requested | closed`
- `assignee_user_id`, `due_at`
- `created_by`, `closed_by`, `closed_at`
- `created_at`, `updated_at`

이슈는 삭제하지 않는다. 잘못 만든 이슈는 사유를 남기고 `closed`로 종료한다.

### `lukas_drawing_issue_anchors`

- `id`, `issue_id`, `project_id`, `file_id`
- `anchor_kind`: `ifc_element | pdf_region`
- IFC: `element_id`, `ifc_global_id`, `camera_json`
- PDF: `page_number`, `x`, `y`, `width`, `height`
- `label`, `created_by`, `created_at`

한 이슈는 여러 IFC 객체와 PDF 영역을 가질 수 있다. 앵커의 파일은 반드시 이슈와 같은 프로젝트에 속해야 한다. 좌표와 식별자는 생성 뒤 수정하지 않고, 잘못된 앵커는 제거 이벤트를 남긴 뒤 비활성화한다.

### `lukas_drawing_issue_comments`

- `id`, `issue_id`, `author_id`, `body`, `created_at`
- 댓글은 append-only이며 수정·삭제하지 않는다.
- 잘못된 댓글의 정정은 새 댓글로 남긴다.

### `lukas_drawing_issue_events`

- `id`, `issue_id`, `actor_id`, `event_type`, `from_value`, `to_value`, `note`, `created_at`
- 상태, 담당자, 기한, 우선순위, 앵커 추가·비활성화를 모두 기록한다.
- 현재 이슈 행은 조회 성능을 위한 현재값이며 이벤트는 감사 근거다.

## 5. 권한

- `owner`: 생성·배정·기한·상태·최종 종료·재개 가능.
- `reviewer`: 생성·배정·검토·최종 종료·재개 가능.
- `estimator`, `site`, `procurement`: 생성·댓글·담당 작업의 `resolution_requested` 전환 가능.
- `viewer`: 조회만 가능.
- 프로젝트 비회원은 모든 테이블과 Storage 원본을 읽을 수 없다.
- 프런트엔드 표시와 별개로 RLS가 동일 권한을 강제한다.
- `anon` 권한은 부여하지 않는다. 공개 공유 링크는 이번 협업실에서 쓰지 않는다.

모든 public 테이블은 RLS를 활성화하고 필요한 `authenticated` 권한만 명시적으로 grant한다. 권한 판정은 기존 `private.lukas_qto_project_role` 계열 helper를 재사용하며 사용자 수정 가능한 metadata는 사용하지 않는다.

## 6. 개정 처리

- 기존 `lukas_qto_file_revisions`가 도면 개정을 정의한다.
- 이슈와 앵커는 생성 당시 file ID에 영구 결합된다.
- 새 개정이 올라오면 이전 개정의 미해결 이슈를 `재검토 필요` 목록에 노출한다.
- IFC는 확인된 Element ID/GlobalId가 새 원본에 정확히 한 번 존재할 때만 `재연결 후보`를 제안한다.
- PDF는 좌표를 새 개정으로 자동 복사하지 않는다. 사용자가 새 페이지/영역을 선택해야 한다.
- 자동 재연결은 승인 권한이 없으며 원본 앵커를 변경하지 않는다.

## 7. 실시간·알림

- 이슈·댓글·이벤트 INSERT/UPDATE를 프로젝트별 Realtime 구독으로 갱신한다.
- 연결이 끊기면 화면에 `실시간 연결 끊김`을 표시하고 일반 재조회로 복구한다.
- 알림함은 내게 배정, 내 이슈 댓글, 해결 요청, 재개 이벤트만 저장한다.
- 이메일은 첫 완성 이후 선택 기능으로 둔다. 앱 안 알림이 먼저다.
- 읽음 상태는 사용자별로 저장하며 프로젝트 전체 이슈 데이터와 분리한다.

## 8. 오류 처리

- 업로드 형식·크기·MIME·원본 SHA를 서버에서 검증한다.
- 렌더러 오류가 나도 파일 정보와 이슈 목록은 계속 열 수 있어야 한다.
- IFC 객체나 PDF 페이지를 찾지 못하면 이슈를 삭제하지 않고 `근거 열기 실패`를 표시한다.
- 동시 상태 변경은 `updated_at` 또는 명시적 version을 조건으로 처리해 뒤늦은 저장이 최신 상태를 덮지 못하게 한다.
- Realtime 이벤트는 UI 갱신 수단일 뿐 저장 성공 판정으로 사용하지 않는다.

## 9. 구현 단계

### D0 — 계약과 안전장치

- 데이터 계약, RLS, 인덱스, 상태 전이 검증 함수, TypeScript 타입을 추가한다.
- 다른 프로젝트 파일·이슈·회원 접근, viewer 쓰기, 비검토자 종료 반례를 자동 검사한다.

### D1 — PDF 도면 기반

- `pdf` 파일 종류와 MIME을 추가한다.
- PDF 페이지 렌더링, 확대·이동·페이지 이동, 정규화 영역 선택을 구현한다.
- 한글·공백 파일명은 기존 opaque Storage key를 사용하고 원명은 metadata에 보존한다.

### D2 — 통합 이슈 협업실

- IFC와 PDF가 같은 이슈 패널·댓글·담당·기한·상태 컴포넌트를 사용한다.
- 앵커 클릭으로 뷰어 위치를 복원한다.
- 프로젝트 홈과 검토 화면을 이슈 데이터로 연결한다.

### D3 — 개정·재검토

- 미해결 이슈의 이전 개정 근거를 표시한다.
- IFC 재연결 후보와 PDF 수동 재연결 흐름을 제공한다.
- 과거 이력과 현재 이슈 수가 정확히 닫히는지 검증한다.

### D4 — 실시간·알림·성능

- 프로젝트별 Realtime 구독, 재연결 상태, 앱 알림함을 추가한다.
- 긴 이슈 목록 pagination, 뷰어 lazy load, PDF 페이지 캐시와 자원 정리를 검증한다.

### D5 — 운영 검증과 출시

- 두 사용자 maker/reviewer 시나리오와 역할별 RLS를 운영 Supabase에서 확인한다.
- 실제 IFC 1개와 다중 페이지 PDF 1개로 이슈 생성→담당→해결 요청→종료→개정 재검토를 실행한다.
- 모바일과 데스크톱에서 동일 이슈가 열리는지 확인한다.
- 배포 후 오류 로그·Realtime 연결·Storage signed URL 만료를 확인한다.

## 10. 수용 기준

1. IFC 객체와 PDF 영역을 하나의 이슈에 동시에 연결할 수 있다.
2. 이슈를 열면 저장 당시 IFC 카메라/객체 또는 PDF 페이지/영역이 보인다.
3. 역할별 허용되지 않은 쓰기는 UI와 RLS 양쪽에서 차단된다.
4. 댓글·상태·담당·기한 변경이 append-only 이벤트로 남는다.
5. 새 개정은 과거 근거를 덮어쓰지 않으며 미해결 이슈를 재검토 대상으로 표시한다.
6. 두 브라우저에서 댓글과 상태가 새로고침 없이 갱신되고, 연결 실패 시 명확한 대체 상태가 보인다.
7. 100MB IFC와 100쪽 PDF에서 첫 화면이 전체 파일 처리 완료를 기다리지 않고 열린다.
8. 프로젝트 외 사용자는 URL을 알아도 이슈·댓글·도면 원본을 읽을 수 없다.
9. 모바일에서 도면 보기, 이슈 작성, 댓글, 해결 요청을 완료할 수 있다.
10. 운영 배포에서 실제 사용자 두 명의 작성·검토·종료 시나리오가 통과한다.

## 11. 이번 범위에서 하지 않는 것

- DWG 네이티브 렌더링
- OCR·AI 도면 인식·자동 이슈 생성
- 자유곡선 드로잉·도형 편집·멀티플레이어 커서
- 화상회의·음성채팅
- 공개 익명 편집
- Go 마이크로서비스 분리

이 기능들은 핵심 협업실이 실제 프로젝트에서 반복 사용되고 병목이나 고객 요구가 증명된 뒤 별도 설계로 추가한다.
