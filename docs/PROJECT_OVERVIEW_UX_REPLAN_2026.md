# Lukas QTO 프로젝트 화면 UX 재기획

기준일: 2026-08-15  
대상: 로그인 후 `/projects/:projectId` 모바일 우선 화면  
현재 단계: UX-P0~P2 화면 구현, UX-P3 실무 검증 준비. 운영 DB 스키마는 변경하지 않음.

## 1. 결론

현재 화면은 기능이 부족한 것이 아니라 **한 화면에 너무 많은 기능이 같은 우선순위로
노출되는 것**이 문제다. 프로젝트에 들어온 사용자는 먼저 아래 세 가지를 알아야 한다.

1. 지금 프로젝트가 어디까지 진행됐는가?
2. 지금 내가 해야 할 한 가지 일은 무엇인가?
3. 문제가 있거나 승인 대기 중인 항목이 몇 개인가?

따라서 프로젝트 첫 화면을 “모든 기능을 실행하는 긴 작업 화면”에서 **프로젝트 요약과
다음 행동을 알려주는 관제 화면**으로 바꾼다. 업로드·산출·검토·자재 기능은 각 업무
화면으로 분리한다.

## 2. 현재 화면에서 확인된 문제

### P0 — 즉시 수정해야 하는 표시 오류

- 앱의 미설정 테마 기본값은 `dark`인데 상단바는 `bg-white/80`, 상태 선택창은
  `bg-white`로 고정되어 있다. 그 결과 흰 글자가 밝은 배경 위에 표시된다.
- 사용자가 테마를 바꿀 수 있는 컴포넌트는 있지만 현재 모바일 내비게이션에서 노출되지
  않는다.
- 모바일에서 `min-width: 720px` 표를 사용하므로 파일 목록은 가로 스크롤을 강제한다.

결정: 운영 화면은 우선 **라이트 모드 기본값**으로 통일한다. 다크 모드는 모든 핵심
화면의 대비·입력·표·상태색 검증이 끝난 뒤 다시 제공한다.

### P1 — 다음 행동이 보이지 않음

- 프로젝트명 아래에 자재, 요소 연결, 구성원, 외부 제안, IDS가 동시에 나온다.
- 실제로 먼저 해야 하는 `IFC 원본 보관`은 첫 화면 아래쪽 카드 안에 숨어 있다.
- 프로젝트 상태 변경은 담당자 설정 기능인데 핵심 작업처럼 첫 화면을 차지한다.
- `프로젝트 설명이 없습니다`는 빈 정보를 안내하는 대신 실패 메시지처럼 보인다.

결정: 첫 화면에는 **서버가 계산한 단 하나의 주 행동**만 강조한다. 나머지는 최대
4개의 바로가기 또는 `전체 도구` 메뉴로 내린다.

### P1 — 긴 단일 페이지

현재 한 페이지에 다음 기능이 모두 있다.

- 원본 업로드와 파일 목록
- 파일 개정 그래프
- 산출 근거 등록·승인
- 내역/QTO 검산 등록·승인
- 규칙 점검과 외부 제안
- 검토 메모와 공유 링크

결정: 첫 화면에서는 요약만 보여주고, 각 기능은 독립 경로에서 필요한 데이터만
불러온다. 모바일에서 스크롤 길이와 인지 부담을 동시에 줄인다.

### P2 — 전문 용어가 너무 일찍 노출됨

- `IDS 요구사항`, `명시적 파일 개정 그래프`, `결정론적 산출 근거`, `SHA`는
  전문가용 상세 정보다.
- 고객은 먼저 `파일`, `물량`, `검토`, `자재`라는 업무 단어를 이해한다.

결정: 기본 화면에서는 쉬운 명칭을 사용한다.

| 현재 문구 | 기본 화면 문구 | 상세 화면에서 유지할 문구 |
|---|---|---|
| 원본 자료 업로드 | 파일 추가 | 원본 무결성·SHA-256 |
| 보관된 원본 | 프로젝트 파일 | 변경 불가 원본 |
| 결정론적 산출 근거 | 물량 산출 결과 | 계산 규칙·입력 확인번호 |
| 내역·QTO 사전검토 | 물량 검산 | 규칙 버전·허용오차 |
| Revit·IFC 요소 연결 | 모델 요소 연결 | Element ID·IFC GlobalId |
| IDS 요구사항 확인 | 설계 요구사항 검사 | buildingSMART IDS 1.0 |
| 자동 검토 제안 | 확인이 필요한 항목 | 생산자·규칙 버전 |

## 3. 실제 데이터가 말하는 빈 상태

운영 Supabase의 프로젝트 12건을 개인정보 없이 집계했다.

- 설명 없음: 7/12
- 담당자 없음: 12/12
- 문의 접수 상태: 11/12
- BIM 모델링 상태: 1/12

따라서 설명·담당자·상태를 첫 화면의 중심 정보로 두면 대부분 빈 값이나 기본값만
보이게 된다. 빈 설명은 숨기고, 권한이 있는 사용자에게만 `프로젝트 정보 보완`을
보조 행동으로 제공한다. 상태 변경은 프로젝트 설정으로 이동한다.

## 4. 새 사용자 흐름

### 화면 1 — 프로젝트 개요

첫 화면의 순서는 고정한다.

1. 프로젝트명 + 현재 단계 배지
2. `지금 할 일` 카드: 주 행동 1개
3. 진행 단계: 파일 → 물량 → 검토 → 자재
4. 주의가 필요한 수치: 미검토, 기각/오류, 승인 대기
5. 최근 활동 3건
6. 바로가기 최대 4개

`지금 할 일` 우선순위 예시:

1. IFC 없음 → `IFC 파일 추가`
2. 요소 원장/QTO 없음 → `Revit 추출 결과 추가`
3. 산출 결과 없음 → `물량 산출 결과 등록`
4. 승인 대기 있음 → `검토 대기 3건 확인`
5. 승인 물량 있고 자재계획 없음 → `자재 계획 만들기`
6. 모두 완료 → `최근 변경 확인`

이 규칙은 숫자를 새로 계산하지 않는다. 현재 Supabase 행의 존재·최신 사람 결정만으로
서버에서 결정한다.

### 화면 2 — 파일

- 모바일 카드 목록, 데스크톱 표
- 종류·파일명·등록일·개정만 기본 표시
- 확인번호는 `원본 상세`에서만 전체 표시
- `파일 추가`를 화면의 단일 주 버튼으로 사용

### 화면 3 — 물량

- 산출 결과와 검산 결과를 탭으로 분리
- 상태 요약을 PASS/검토 필요/오류의 쉬운 문구로 표시
- 등록과 승인 행동을 같은 카드에 섞지 않고 `결과 보기 → 결정 기록` 순서로 진행

### 화면 4 — 검토

- 승인 대기 항목을 먼저 표시
- 규칙 경고, 검토 메모, 개정 차이를 하나의 작업 목록으로 합쳐 보임
- 외부 모델 제안은 한길 담당자·기능 플래그가 모두 참일 때만 별도 필터로 표시

### 화면 5 — 자재

- 기존 자재·발주·입고 화면을 유지
- 프로젝트 개요에는 승인 물량 이후에만 바로가기를 강조

### 전체 도구

구성원, 모델 요소 연결, IDS, 공유 링크, 프로젝트 설정, 담당자용 파일럿은 `전체 도구`
안으로 이동한다. 권한이 없는 도구는 아예 표시하지 않는다.

## 5. 모바일 내비게이션

하단 고정 메뉴를 5개로 제한한다.

- 개요
- 파일
- 물량
- 검토
- 자재

승인할 항목이 있으면 `검토`에 숫자 배지를 붙인다. `전체 도구`는 개요의 보조 영역에
둔다. 데스크톱에서는 같은 구조를 좌측 사이드바로 확장한다.

## 6. 시각 방향

방향명: **Bright Operations**

- 업무 화면은 밝은 회색 바탕과 흰 카드 사용
- 브랜드 보라색은 주 행동·현재 단계에만 사용
- 성공=초록, 주의=주황, 오류=빨강을 의미 색으로 제한
- 모바일 좌우 여백 16px, 카드 간격 12px, 카드 radius 16px
- 모든 터치 대상 최소 44×44px
- 한 카드에는 주 버튼 하나만 배치
- Glass 효과는 상단바의 약한 투명도에만 사용하고 본문 카드에는 사용하지 않음
- `SHA-256`, 규칙 해시, 내부 버전은 접힌 `근거 상세` 안으로 이동

## 7. Supabase 적용 원칙

### 1차 개편 — 스키마 변경 없음

- 현재 파일, 산출 결과, 검산 결과, 사람 결정, 자재 계획을 loader에서 병렬 조회한다.
- `지금 할 일`과 요약 수치는 서버에서 파생한다.
- RLS는 기존 프로젝트 역할 정책을 그대로 사용한다.
- 사용자 권한에 없는 바로가기는 SSR 단계부터 반환하지 않는다.

### 2차 개편 — 실제 사용량 확인 후

최근 활동 조회가 느려질 때만 읽기 전용 activity projection을 검토한다. public view가
필요하면 `security_invoker = true`와 기존 RLS를 전제로 하며, 단순 UX 개선 때문에
SECURITY DEFINER 함수나 새 공개 API를 만들지 않는다.

### 최신 운영 기술 조건

- Supabase JS는 2026-06-30 이후 Node.js 20 지원을 종료했으므로 Vercel 런타임을
  Node.js 22 이상으로 명시한다.
- 인증된 프로젝트 화면은 CDN 캐시 대상이 아니어야 하며, Supabase client는 현재처럼
  요청마다 생성한다.
- SSR 쿠키 세션은 `@supabase/ssr`의 PKCE 흐름을 유지한다.

## 8. 구현 순서

### UX-P0 — 깨진 인상 제거

- 라이트 기본 테마
- 상단바·상태 선택 대비 수정
- 빈 설명 문구 제거
- 모바일 첫 화면에서 상태 변경 폼과 기술 도구 제거

완료 조건: 390px 화면에서 흰색 입력창의 글자가 보이고 가로 스크롤이 없다.

### UX-P1 — 프로젝트 개요 재구성

- `지금 할 일` 결정 함수
- 4단계 진행 표시
- 승인 대기·오류·파일 수 요약
- 최근 활동 3건
- 역할별 바로가기 최대 4개

완료 조건: 신규 사용자가 첫 화면 5초 안에 다음 행동을 말할 수 있다.

### UX-P2 — 긴 페이지 분리

- `/projects/:id/files`
- `/projects/:id/quantities`
- `/projects/:id/reviews`
- 기존 `/materials` 연결
- 모바일 하단 내비게이션과 데스크톱 사이드바

완료 조건: 각 업무 화면은 해당 업무 데이터만 조회하고, 기본 행동까지 두 번 이하의
탭으로 도달한다.

### UX-P3 — 실무 검증

- 적산 담당자 3명에게 다음 과제를 제공: IFC 추가, 산출 결과 찾기, 승인 대기 처리
- 과제 성공률, 첫 행동까지 시간, 잘못 누른 메뉴, 포기 지점을 기록
- 용어는 인터뷰 결과로 한 번 더 정리

완료 조건: 핵심 과제 3개 성공률 90% 이상, 첫 행동 중앙값 10초 이하.

## 9. 비교 조사에서 가져올 것

- Autodesk Construction Cloud 모바일은 프로젝트 홈에서 최근 파일, 작업 상태, 최대
  4개의 사용자별 바로가기를 제공하고 나머지 도구는 More로 보낸다.
- Autodesk/BIM 360은 역할과 권한에 따라 카드와 할 일을 다르게 보여주며 핵심 질문을
  `오늘 내가 해야 할 일은 무엇인가`로 둔다.

  `어느 원본에서 나온 결과이며 무엇이 바뀌었는가`를 기본 문장으로 보여준다.

## 10. 이번 감사의 한계

- 제공된 모바일 첫 화면과 현재 소스 구조를 기준으로 진단했다.
- 로그인 뒤 전체 클릭 흐름, 키보드 탐색, 스크린리더 읽기 순서, 실제 터치 성공률은 아직
  측정하지 않았다.
- 따라서 WCAG 준수 판정이 아니라 명백한 대비·반응형·정보 구조 위험을 정리한 것이다.
