## 2. 제품 경계

### Revit 애드인

- 원본 Properties, QTO, IFC, element ledger를 추출하는 역할만 맡는다.
- 품목·단가·금액을 계산하거나 승인하지 않는다.
- 기존 설치본과 추출 흐름을 계속 독립적으로 업데이트한다.

### 웹 플랫폼

- 승인된 원수량을 읽고 품목 매핑, 보정, 단가 적용, 내역 계산, 검토, 승인, Excel 출력을 맡는다.
- 이번 BOQ 계산은 서버측 exact-decimal 구현 하나만 정본으로 둔다.
- 같은 BOQ 계산엔진을 애드인·Desktop·브라우저에 동시에 복제하지 않는다.
- 브라우저 부동소수점으로 최종 수량이나 금액을 확정하지 않는다.

### 참고와 복제의 경계

- XCost에서 참고할 것은 `프로젝트→수량→품목→단가→내역→Excel`의 실무 흐름,
  통합 검색, 이전 프로젝트 복사, 오류 목록, 개정 비교다.
- XCost의 제품명, 문구, 화면 배치, 아이콘, 색, 산식 템플릿, 샘플 데이터와 단가 DB를
  복사·스크래핑·재배포하지 않는다.

## 3. 첫 사용자와 해결할 문제

첫 사용자는 적산 실무자 또는 견적 담당자다. 이 사용자는 Revit/IFC에서 나온 수량은 있지만,
그 수량을 내역 품목과 단가에 연결하고 검토 가능한 Excel로 만드는 과정이 수작업이다.

첫 출시가 해결해야 하는 질문은 다섯 가지다.

1. 이 내역 수량은 어느 Revit/IFC 요소에서 왔는가?
2. 원수량에서 무엇을 더하거나 뺐는가?
3. 어떤 단가표와 어떤 계산 방식으로 금액을 만들었는가?
4. 이전 개정과 수량·금액이 왜 달라졌는가?
5. 누가 검토하고 승인했는가?

## 4. 반드시 완성할 사용자 흐름

1. 프로젝트와 원본 개정을 선택한다.
2. Revit 패키지 또는 이미 승인된 QTO를 가져온다.
3. 내역 체계(WBS/공종/품목)를 새로 만들거나 CSV/XLSX에서 가져온다.
4. 원수량 행을 품목에 연결한다.
   - 1:1 연결
   - 여러 원수량의 합계
   - 한 원수량의 계수 기반 분할
   - 제외 + 필수 사유
5. 사용자 소유 단가표를 가져오거나 직접 입력한다.
6. 품목에 재료·노무·장비/경비 자원과 소요계수를 연결하고 직접공사비를 결정론적으로 계산한다.
7. 내역 행을 누르면 다음 근거를 한 화면에서 확인한다.
   - 원수량과 보정수량
   - 계산식과 반올림 방식
   - 단가표 이름·버전·기준일
   - Revit Element ID 또는 IFC GlobalId
   - 3D IFC 요소 강조
   - 원본 파일 고유 확인번호
8. 작성자와 다른 검토자가 승인 또는 반려한다.
9. 승인된 버전을 잠그고 Excel/CSV와 실행기록 manifest를 내려받는다.
10. 새 설계 개정이 들어오면 기존 승인본을 수정하지 않고 새 버전을 만들며,
    수량·단가·금액 증감을 원인별로 보여준다.

## 5. 최소 데이터 계약

현재 Supabase 구조를 먼저 확인하고 가능한 한 기존 project/file/revision/approval 구조를 재사용한다.
새 migration은 추가형으로만 만든다. 기존 테이블 삭제, 기존 컬럼 의미 변경, 파괴적 migration은 금지한다.

논리적으로 다음 값은 반드시 분리한다.

- 원수량: 추출 원본에서 온 불변 값
- 보정: signed 값, 사유, 작성자, 작성시각
- 최종수량: 원수량과 승인된 보정 및 명시적 반올림으로 계산된 값
- 품목: 코드, 품명, 규격, 단위, 공종/WBS
- 단가표: 소유자, 이름, 버전, 기준일, 통화, 출처 메모
- 자원: 코드, 유형(material/labor/equipment/expense), 품명, 규격, 단위, 단가
- 일위대가 구성: 품목, 자원, 소요계수, 구성금액
- 매핑: 원수량 참조, 품목 참조, 계수, 포함/제외, 사유
- 내역 버전: DRAFT, IN_REVIEW, APPROVED, SUPERSEDED
- 승인 이벤트: append-only 작성·요청·승인·반려 기록
- 근거: source file/revision, Element ID/IFC GlobalId, 계산규칙 버전

원수량을 사용자의 수정값으로 덮어쓰지 않는다. 승인된 내역도 직접 수정하지 않고 새 버전을 만든다.
모든 내역 행은 원본 요소 또는 `수동 입력 + 사유 + 작성자` 중 하나로 역추적돼야 한다.

## 6. 최소 계산 계약

첫 버전은 고객이 제공하거나 직접 입력한 단가만 사용한다.
숨은 품셈, 추정 손율, 자동 공제, 임의 시장단가는 적용하지 않는다.
단가표에는 버전·기준일·출처와 `customer_owned`, `licensed`, `public_authorized` 중 하나의
권리 근거가 있어야 한다. 제품이 단가 자료의 최신성이나 공인 기준 적합성을 보증한다고 표시하지 않는다.

지원 단위는 현재 검증 가능한 `EA`, `m`, `m2`, `m3`로 제한한다.

기본 계산은 다음을 명시적으로 기록한다.

- `mapped_quantity = source_quantity × mapping_coefficient`
- `raw_quantity = Σ(mapped_quantity)`
- `final_quantity = Round(raw_quantity + Σ(signed_adjustment), quantity_scale, quantity_rounding)`
- `component_unit_amount = PriceRound(resource_coefficient × resource_unit_price)`
- `material_unit_price = Σ(material component_unit_amount)`
- `labor_unit_price = Σ(labor component_unit_amount)`
- `expense_unit_price = Σ(equipment/expense component_unit_amount)`
- `unit_price = material_unit_price + labor_unit_price + expense_unit_price`
- 일반 내역: `amount = Round(final_quantity × unit_price, amount_scale, amount_rounding)`
- EMS 호환 검산: `amount = TRUNC(Q×M,0) + TRUNC(Q×L,0) + TRUNC(Q×E,0)`

어느 모드를 사용했는지 내역 버전에 고정한다. 반올림 방식·자리수·적용 순서를 화면과 결과물에 남긴다.
같은 입력 파일, 매핑, 단가표, 규칙 버전은 항상 같은 canonical 결과를 만들어야 한다.

첫 버전에서 계산하는 금액은 직접공사비까지다. 간접비, 일반관리비, 이윤, 부가세,
표준품셈 적정성은 별도 승인 규칙과 법적 근거가 생길 때까지 자동 확정하지 않는다.

## 7. 오류와 검토 규칙

다음은 계산을 차단한다.

- 원수량 파일 또는 개정 근거가 없음
- 품목 단위와 원수량 단위가 다름
- 같은 원수량이 사유 없이 중복 계상됨
- 품목 코드·단가표 버전·계산 모드가 없음
- 음수 단가, 허용하지 않은 단위, 유효하지 않은 decimal
- 매핑 계수가 0 이하임
- 승인된 버전을 직접 수정하려 함

다음은 `확인 필요`로 남기며 자동 PASS로 만들지 않는다.

- 미매핑 원수량
- 제외 사유가 모호함
- 단가 출처 메모 또는 기준일 누락
- 수동 입력이 원본 요소와 연결되지 않음
- 개정 전후 큰 증감의 설명이 없음

내부 화면에는 PASS/REVIEW/SHA 같은 용어보다 `계산 가능`, `확인 필요`,
`승인 완료`, `파일 고유 확인번호`를 먼저 보여준다.

## 8. UX 계약

주 작업 화면은 다섯 단계로 고정한다.

1. 원본 수량
2. 품목 연결
3. 단가 적용
4. 검토·승인
5. Excel 내보내기

- 사용자가 현재 해야 할 행동 하나를 화면 상단에 보여준다.
- 미매핑 개수, 단위 오류, 승인 대기를 항상 요약한다.
- 품목 검색과 매핑은 키보드 중심 대량 작업을 지원한다.
- 원수량·보정·최종수량은 한 열로 섞지 않는다.
- 내역 행에서 IFC 3D 요소와 계산 근거로 바로 이동한다.
- 해시 전체값은 기본 화면에서 숨기고 상세 근거에서만 복사 가능하게 한다.
- 모바일은 조회·검토·승인에 집중하고 대량 매핑과 단가 편집은 데스크톱을 우선한다.
- 빈 화면에는 설명문이 아니라 `첫 원수량 가져오기` 같은 실제 다음 행동을 표시한다.
- 한글 파일명은 화면에 보존하되 Storage object key는 UUID 기반 ASCII 경로를 사용한다.

## 9. 보안·무결성 계약

- IFC, 단가표, 내역 원본은 private storage에 둔다.
- 다운로드와 IFC 조회는 짧은 signed URL을 사용한다.
- 조직·프로젝트 권한은 UI가 아니라 Supabase RLS와 서버에서 함께 검증한다.
- 계산·승인 action은 서버에서 입력을 다시 검증한다.
- 원본, 매핑, 단가표, 계산규칙, 결과의 고유 확인번호를 실행기록에 묶는다.
- 작성자는 자기 결과를 최종 승인할 수 없다.
- CSV 수식 주입, 한글 인코딩, 선행 0 품목코드, 숫자 로캘을 회귀 테스트한다.
- Excel 파일만 믿지 않고 동일 내용을 기계 검증 가능한 CSV/manifest로 함께 출력한다.

## 11. 단계별 목표와 게이트

### B0. 현행 보호

- 현재 로그인, 프로젝트, 파일 업로드, IFC 뷰어, Revit 다운로드, 추출, 승인 흐름을 고정한다.
- 현재 자동 테스트와 실제 배포 URL을 기록하고 rollback 방법을 만든다.
- 실패 시 새 BOQ 개발을 중지하고 회귀부터 고친다.

완료 증거: 기존 Core/CLI/Desktop/platform/field-kit 테스트와 production smoke 결과.

### B1. 골든 데이터 고정

- 실제 유치원 프로젝트에서 사용자가 승인한 원수량과 기준 내역서의 작은 대표 범위를 고정한다.
- 단위, 공제, 할증, 반올림 위치, 기대 금액, 원본 요소를 문서화한다.
- 기존 EMS 0910 계산과 80,487,000원 결과는 현재 L1 검산으로 먼저 재현한다.
- 근거 없는 값을 새 제품의 정답으로 만들지 않는다.

완료 증거: 변경 불가능한 fixture, 기대 결과, 전문가 확인 메모.

### B2. 도메인 계약과 최소 저장

- 원수량·보정·매핑·품목·단가표·내역버전·승인을 분리한다.
- 기존 구조를 재사용하고 최소한의 추가 migration과 RLS만 만든다.
- 승인본 불변성과 버전 복제를 검증한다.

완료 증거: migration/RLS 테스트, rollback 문서, 비소유자 접근 거부 테스트.

### B3. 한 공종 수직 기능

- 골든 fixture의 한 공종만 대상으로 수량 가져오기, 수동 매핑, 단가 입력, 계산을 완성한다.
- 미매핑·중복·단위 불일치를 즉시 보여준다.
- 결과 행에서 원본 요소와 산식을 확인한다.
- 가상 데모 단가만 사용한 고정 계산 벡터를 통과한다.
  `수량 10m3 × (재료 100,000 + 노무 10,000 + 경비 5,000) = 1,150,000원`.
  이 수치는 시장단가가 아니라 계산 회귀용 fixture임을 명시한다.

완료 증거: 동일 입력의 canonical 결과 일치, decimal 경계 테스트, IFC 요소 드릴다운.

### B4. 검토·승인·Excel

- maker-checker 검토, 반려 메모, 승인 잠금, Excel/CSV/manifest 출력을 완성한다.
- Excel을 다시 읽어 품목코드·한글·수량·단가·금액이 보존되는지 검증한다.

완료 증거: 작성자 자기승인 차단, 승인본 수정 차단, export round-trip 테스트.

### B5. 개정 비교

- 이전 승인본을 복제해 새 원수량·단가표와 연결한다.
- 수량 변화, 단가 변화, 매핑 변화, 수동 보정을 별도 원인으로 분해한다.
- 행별 증감 합계와 전체 증감이 정확히 닫혀야 한다.

완료 증거: 추가·삭제·변경 fixture와 설명 가능한 수량·금액 delta.

### B6. 실무 파일럿

- 적산 실무자 3명이 안내 없이 다음 과제를 수행한다.
  `파일 등록→품목 연결→단가 적용→근거 확인→검토 승인→Excel 다운로드`
- 실패 지점, 소요 시간, 잘못된 클릭과 용어 혼란을 기록하고 수정한다.
- 골든 내역과의 차이를 계산 버그, 정책 차이, 입력 차이로 분류한다.

완료 증거: 세 사용자 과제 기록과 설명되지 않은 수치 차이 0건.

## 12. 에이전트 운영 방식

총괄은 하나의 backlog와 완료 기준을 유지한다. 병렬 에이전트는 독립적인 일에만 사용한다.

- 계약·골든 데이터 에이전트: 기존 수치와 계산식을 읽기 전용으로 검증
- DB/RLS 에이전트: 추가형 migration과 조직 격리 테스트만 담당
- 계산 에이전트: exact-decimal 순수 함수와 계산 벡터만 담당
- UX 에이전트: 한 단계 화면과 접근성 테스트만 담당
- 감사 에이전트: 변경 파일 밖에서 적대적 반례와 회귀 확인

각 요청에는 목표, 허용 파일, 금지 파일, 실행 테스트, 완료 증거를 적는다.
같은 파일을 두 에이전트가 동시에 수정하게 하지 않는다. 총괄은 결과를 현재 트리에서 다시 검증한다.
한 단계가 닫히기 전에 다음 단계의 추상화나 화면을 선행 구현하지 않는다.

## 13. 출시 금지 조건

- 단가·품셈의 출처와 사용권이 불명확함
- 원수량이 수정값으로 덮어써짐
- 내역 행에서 원본 요소·산식·단가표 버전을 확인할 수 없음
- 공제·할증·반올림 순서가 문서화되지 않음
- 같은 입력이 실행마다 다른 금액을 만듦
- 조직 간 RLS 또는 signed URL 테스트가 실패함
- 승인본을 수정할 수 있거나 작성자가 자기승인할 수 있음
- 기존 프로젝트, IFC 뷰어, Revit 애드인 또는 다운로드가 깨짐
- 골든 데이터와 설명되지 않는 차이가 남음
- 실제 검증 없이 `자동`, `정확`, `공식 견적`이라고 표시함

## 14. 완료 정의

페이지나 테이블이 생긴 것으로 완료하지 않는다.

실제 프로젝트 1건이 기존 Revit 애드인에서 추출되고, 웹에서 원수량을 보존한 채 품목과
사용자 단가를 연결하며, 각 금액의 원본 요소·산식·규칙·단가표 버전을 확인하고,
다른 사용자의 승인 후 재현 가능한 Excel 내역서를 내려받을 수 있을 때 완료다.

자동 테스트만 통과하면 CODE_GO다. 실무자 3명 파일럿 전에는 READY_FOR_PILOT,
세 과제와 골든 데이터가 통과한 뒤에만 PILOT_VERIFIED다.
